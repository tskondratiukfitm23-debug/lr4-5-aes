# Етап 3. Швидкодія та споживання ресурсів

Код: `aeslab/benchmark.py` (точка входу — `benchmark.py`). Повні результати: `outputs/benchmark_results.md`, `outputs/benchmark_results.csv`, `outputs/benchmark_kdf.csv`, графіки `outputs/benchmark_*.png`.

## 3.1. Методика

* Файли з випадкових даних: 1 KB, 100 KB, 1 MB, 10 MB, 50 MB. Генеруються в `bench_data/` (не в git) і видаляються після прогону.
* Для кожного розміру й режиму: прогрів, потім 5 повторів шифрування й дешифрування повного файлу через той самий рушій, що й у CLI (з атомарним записом).
* Метрики: час `perf_counter` (середнє ± σ), CPU-час `process_time`, пропускна здатність MiB/s, пік пам'яті `tracemalloc` (окремий прохід), `ru_maxrss` процесу, накладні витрати розміру (заголовок + тег).
* Правильність кожного round-trip перевіряється SHA-256.
* Ключ 256 біт без KDF, щоб виміряти саме шифр. Вартість KDF вимірюється окремо.
* Середовище еталонного прогону: Intel Xeon 6975P-C (AES-NI, PCLMULQDQ), Python 3.11, cryptography 50.0.2, OpenSSL 4.0.3. На іншому обладнанні (наприклад, у ВМ VirtualBox) абсолютні значення відрізнятимуться, але співвідношення між режимами зберігаються.

Запуск:
```bash
python3 benchmark.py                                   # повний набір
python3 benchmark.py --sizes 1KB 1MB 10MB --repeat 3   # швидкий
python3 benchmark.py --modes aes-gcm aes-cbc-hmac --fsync
```

## 3.3. Порівняння за безпекою

| Режим | Паралелізм шифр./дешифр. | Проходів шифр./дешифр. | Наслідок повтору nonce/IV | Головні ризики |
|---|---|---|---|---|
| aes-gcm | так / так | 1 / 1 | катастрофічний: XOR текстів + підробка тегів | ліміт 2^32 повідомлень, ≤64 GiB/повідомлення |
| aes-cbc-hmac | ні / так | 1 / 2 | витік спільних префіксів | padding oracle без EtM; IV має бути непередбачуваним |
| aes-ctr-hmac | так / так | 1 / 2 | повтор гами (XOR текстів) | пластичність без MAC |
| aes-cfb-hmac | ні / так | 1 / 2 | витік першого блоку | послідовний, застарілий |
| chacha20-poly1305 | між сегментами | 1 / 1 | катастрофічний | не FIPS, лише 256 біт |
| aes-gcm-siv | ні / між сегментами | 2 / 1 | лише рівність повідомлень | повільніший, OpenSSL ≥ 3.2 |

## 3.4. Висновки про доцільність

1. **AES-GCM** — режим за замовчуванням. Він найшвидший завдяки AES-NI + PCLMULQDQ, працює за один прохід і стандартизований NIST. Умови: унікальний nonce (контролюється keystore) і тег 128 біт.
2. **AES-CBC + HMAC (EtM)** безпечний, але в 3–4 рази повільніший за GCM: шифрування послідовне, дешифрування двопрохідне. Доцільний для сумісності з легасі.
3. **AES-CTR/CFB + HMAC** коректні, проте переваг над GCM не мають. CFB найменш доцільний.
4. **AES-GCM-SIV** варто обирати, коли унікальність nonce гарантувати неможливо (розподілені системи, клоновані ВМ). Ціна — найнижча швидкість.
5. **ChaCha20-Poly1305** підходить для платформ без AES-NI (ARM, вбудовані системи) і як не-AES резерв.
6. **Пам'ять** у потокових режимів стала (≈ буфер 1 MiB, у сегментованих — ≈ 2 сегменти по 64 KiB) і не залежить від розміру файлу, тож придатна для файлів будь-якого розміру.
7. **KDF**: 310 000 ітерацій PBKDF2 ≈ 38 мс на розблокування, тобто ≈ 26 спроб перебору за секунду на ядро. scrypt додатково дорожчий для GPU/ASIC.
