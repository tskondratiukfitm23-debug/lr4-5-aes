# Етап 1. Генерування, зберігання та життєвий цикл ключів

Код: `aeslab/keystore.py`, `aeslab/config.py`. Тести: `tests/test_keys.py`.

## 1.1. Схема виведення ключів

```
пароль ──PBKDF2-HMAC-SHA256 (310 000 ітерацій, випадковий salt 16 B)──► master (32 B)
        (або scrypt N=2^15, r=8, p=1, ≈32 MiB RAM)
master ──HKDF-SHA256(info="aeslab/v2/verifier")──────► verifier (32 B, зберігається)
master ──HKDF-SHA256(info="aeslab/v2/key-id")────────► key_id (8 B, публічний відбиток)
master ──HKDF-SHA256(info="aeslab/v2/<режим>/<біт>")─► enc_key (16/24/32 B) ‖ mac_key (32 B)
```

* **Випадковий salt** — `os.urandom(16)` (CSPRNG ОС, 128 біт). Однаковий пароль дає різні ключі, тож райдужні таблиці не працюють.
* **Контроль довжини ключа.** Дозволено лише AES-128/192/256 (16/24/32 байти). Функція `check_key()` перевіряє довжину перед кожною операцією, а `resolve_params()` — сумісність довжини з режимом. Наприклад, ChaCha20 підтримує лише 256 біт, AES-GCM-SIV — 128/256. Ключ HMAC завжди ≥ 256 біт.
* **Розділення ключів (domain separation).** Ключ шифрування і ключ MAC — різні. Для кожного режиму й довжини виводиться окрема пара, тож один і той самий ключ ніколи не використовується двома алгоритмами (захист від міжпротокольних атак).
* **Verifier.** Неправильний пароль виявляється ДО дешифрування (код `WRONG_PASSWORD`), а не як «зіпсований тег». Порівняння виконується через `hmac.compare_digest` (константний час).
* **У `keystore.json` НЕ зберігаються** пароль, master чи робочі ключі. Там лише salt, параметри KDF, verifier, метадані й лічильники. Файл записується атомарно (тимчасовий файл + `os.replace`) з правами `0600`.

## 1.2. Процедура ініціалізації

1. Створити віртуальне середовище й встановити залежності (див. README).
2. Задати пароль у змінну середовища (не в аргументах командного рядка, щоб він не потрапив в історію shell):
   ```bash
   read -rs AES_LAB_PASSWORD; export AES_LAB_PASSWORD
   ```
   Якщо змінна не задана, CLI запитає пароль через `getpass` (без відлуння).
3. Створити ключ:
   ```bash
   python3 aes_cli.py key new --label lab-main --expires-days 180 --max-uses 100000
   # варіанти: --kdf scrypt | --iterations 600000 | --key-bits 128/192/256
   ```
4. Перевірити:
   ```bash
   python3 aes_cli.py key list
   python3 aes_cli.py key verify --label lab-main
   ```

**Політика пароля:** щонайменше 12 символів і 3 з 4 класів (малі, великі літери, цифри, символи). Слабкий пароль відхиляється з кодом `WEAK_PASSWORD`.

## 1.3. Запобігання повторному використанню ключа

| Механізм | Що блокує | Код помилки |
|---|---|---|
| Унікальність мітки (лише один `active` ключ на мітку) | дубль ключа під тією ж назвою | `KEY_REUSE` |
| Унікальність salt і key_id у сховищі | повторне створення того самого ключа | `KEY_REUSE` |
| Перевірка, що новий пароль не відкриває жоден наявний ключ (вимикається `--no-reuse-check`) | повторне використання пароля | `KEY_REUSE` |
| Кеш відбитків останніх 1000 IV/nonce на ключ | повтор nonce (зламаний RNG, клонування ВМ) | `NONCE_REUSE` |
| Лічильник викликів GCM, ліміт 2^32 (NIST SP 800-38D, п. 8.3) | перевищення ліміту випадкових nonce | `NONCE_LIMIT` |
| `max_uses` — ліміт операцій шифрування | надмірне навантаження на ключ | `KEY_EXHAUSTED` |
| `expires_at` — термін дії (за замовчуванням 180 днів) | використання застарілого ключа | `KEY_EXPIRED` |

Лічильник використання й відбиток nonce фіксуються **до** шифрування. Навіть якщо операція перерветься, nonce уже вважається використаним.

## 1.4. Життєвий цикл ключа

```
 key new          key rotate               key revoke
──────► ACTIVE ───────────────► RETIRED ─────────────► REVOKED (кінцевий стан)
          │  (шифрування +        (лише дешифрування      (будь-яке використання
          │   дешифрування)        старих файлів)          заборонене, KEY_REVOKED)
          └──────────────── key revoke (компрометація) ──────────►
```

| Стан | Шифрування | Дешифрування | Як потрапити |
|---|:--:|:--:|---|
| `active` | так | так | `key new`, `key rotate` (новий ключ) |
| `retired` | ні | так | `key rotate` (старий ключ), `key retire` |
| `revoked` | ні | ні | `key revoke --reason ...` (повернення неможливе) |

**Правила:**
1. Ротація — щонайменше раз на 180 днів, після досягнення `max_uses` або 2^32 викликів GCM, а також при зміні персоналу з доступом до пароля.
2. Після ротації старі файли перешифровуються командою `rekey` (старий пароль — `AES_LAB_OLD_PASSWORD`, новий — `AES_LAB_PASSWORD`). Потім старий ключ можна відкликати.
3. При підозрі на компрометацію: негайно `key revoke`, перешифрувати дані новим ключем, проаналізувати журнал (`log_analyzer.py`).
4. Сховище `keystore.json` — у `.gitignore`. Резервна копія зберігається окремо від зашифрованих даних.
5. Кожна зміна стану (`key_create`, `key_rotate`, `key_revoke`, `key_unlock`, `key_warning`) записується в журнал.
