# Етап 5. Журналювання, обробка аномалій, аналіз логів

Код: `aeslab/logging_setup.py`, `aeslab/errors.py`, `aeslab/log_analyzer.py` (точка входу — `log_analyzer.py`). Приклад звіту: `outputs/log_report.md`.

## 5.1. Формат журналу

`logs/aes.jsonl`: один JSON-об'єкт на рядок, час UTC. Ротація — `RotatingFileHandler`, 1 MiB × 5 копій. Каталог `logs/` створюється автоматично.

```json
{"ts":"2026-11-24T20:20:56.587Z","level":"ERROR","event":"decrypt","session":"251aa0355a49",
 "pid":5545,"user":"ubuntu","op":"decrypt","key_id":"5b3ef446988dd614","label":"lab-main",
 "in_file":"sample_gcm_tampered.enc","in_size":448,"in_sha256":"d2f4…","mode":"aes-gcm",
 "status":"fail","error_code":"TAMPER_DETECTED",
 "error":"Виявлено втручання: тег автентичності не збігся (дані/заголовок змінено або інша AAD)",
 "duration_s":0.00074}
```

| Поле | Призначення |
|---|---|
| `ts`, `session`, `pid`, `user` | хто, коли й у межах якого запуску |
| `event`, `op`, `status` | що сталося (`encrypt`, `decrypt`, `rekey`, `key_*`, `repl_*`, `tamper_test`, `insecure_demo`) і з яким результатом |
| `key_id`, `label`, `mode`, `key_bits`, `padding`, `tag_len`, `aad` | ключ і параметри (без секретів) |
| `in_file`, `in_size`, `in_sha256`, `out_sha256` | ідентифікація даних для розслідування |
| `error_code`, `error` | класифікована помилка |
| `duration_s`, `cpu_s` | продуктивність і виявлення аномалій часу |

**Ніколи не журналюються:** паролі, майстер-ключ, робочі ключі, відкритий текст. Повні шляхи також не записуються, лише імена файлів.

**Рівні:** `INFO` — успішні операції; `WARNING` — попередження політик (ключ скоро закінчиться, незахищені права keystore, демо без MAC); `ERROR` — невдалі операції.

## 5.2. Класифікація помилок у даних

| Код | Ситуація | Повідомлення користувачу |
|---|---|---|
| `TAMPER_DETECTED` | пароль підтверджено, але тег/HMAC не збігся | «Виявлено втручання: тег автентичності не збігся…» |
| `AUTH_FAILED` | тег не збігся, ключ не підтверджено | неможливо відрізнити неправильний ключ від підміни |
| `WRONG_PASSWORD` | verifier не збігся (до дешифрування) | «Неправильний пароль» |
| `BAD_MAGIC` / `BAD_FORMAT` | не контейнер AES-Lab / зіпсований заголовок | — |
| `TRUNCATED` | файл обрізано | — |
| `KEY_MISMATCH` / `KEY_NOT_FOUND` | key_id файлу не відповідає ключу | — |
| `BAD_PADDING` | некоректне доповнення (можливе лише після успішного MAC → помилка реалізації) | — |

Чому `TAMPER_DETECTED` і `AUTH_FAILED` розділено: з погляду криптографії неправильний ключ і підміна даних дають однаково випадковий тег. Завдяки verifier програма знає, що ключ правильний, і тоді впевнено повідомляє саме про підміну.

## 5.3. Інструкція з аналізу журналу

**Автоматично:**
```bash
python3 log_analyzer.py --log logs/aes.jsonl --out outputs/log_report.md
# пороги: --auth-threshold 5 --auth-window 60 --pw-threshold 5 --pw-window 300
```

Звіт містить аномалії, події, рівні, операції за статусом, режими, ключі, коди помилок і останні невдалі операції.

| Правило | Важливість | Що виявляє | Реакція |
|---|---|---|---|
| A1 | ВИСОКА | серія `TAMPER_DETECTED`/`AUTH_FAILED` для одного key_id за короткий час | ізолювати джерело файлів, перевірити канал передавання, порівняти `in_sha256` з еталоном |
| A2 | ВИСОКА | серія `WRONG_PASSWORD` | можливий підбір пароля: обмежити доступ до keystore, змінити пароль (ротація) |
| A3 | КРИТИЧНА | використання відкликаного ключа | розслідувати, хто й навіщо; ключ міг бути скомпрометований |
| A4 | КРИТИЧНА | `NONCE_REUSE` | перевірити RNG / клонування ВМ, негайна ротація |
| A5 | СЕРЕДНЯ | багато пошкоджених або чужих файлів у сесії | помилка процесу чи сканування |
| A6 | НИЗЬКА/ІНФО | небезпечні практики (права keystore, демо без MAC) | виправити конфігурацію |

**Вручну (jq / grep):**
```bash
jq -c 'select(.status=="fail") | {ts,event,mode,key_id,error_code,in_file}' logs/aes.jsonl | tail
jq -r 'select(.error_code) | .error_code' logs/aes.jsonl | sort | uniq -c | sort -rn
jq -c 'select(.error_code=="TAMPER_DETECTED")' logs/aes.jsonl
grep -c '"level": "ERROR"' logs/aes.jsonl
```

**Результат на демонстраційному журналі** (499 записів, `outputs/log_report.md`): 7 аномалій — 2 критичні (A3 — відкликаний ключ, A4 — повтор nonce), 3 високі (A1 ×2 — серії збоїв автентичності під час tamper-тестів і padding-oracle, A2 — підбір пароля), 1 середня (A5), 1 інформаційна (A6).

## 5.4. Як журнали посилюють безпеку

1. **Виявлення атак.** Одиночний збій тегу може бути випадковим пошкодженням, а серія — ознакою цілеспрямованої підміни чи оракульної атаки. Без журналу такі серії непомітні.
2. **Розслідування інцидентів.** `session`, `user`, `in_sha256`, `key_id` дозволяють відновити хронологію: хто, коли, яким ключем і над яким файлом виконував операцію.
3. **Контроль життєвого циклу ключів.** Журнал фіксує створення, ротацію, відкликання й спроби використати відкликаний ключ, що потрібно для аудиту (ISO/IEC 27001 A.8.15, A.8.24).
4. **Виявлення неправильної конфігурації**: повтор nonce, слабкі права файлів, небезпечні режими.
5. **Підзвітність і неспростовність**: кожна дія прив'язана до сесії й користувача.
6. **Захист самих журналів.** Секретів у журналі немає, тож його можна передавати в SIEM. Рекомендується пересилати журнал на віддалений сервер (syslog/SIEM) з обмеженим доступом, щоб зловмисник не міг стерти сліди.
